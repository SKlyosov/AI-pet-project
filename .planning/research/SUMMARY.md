# Project Research Summary

**Project:** Private Classifieds (Частные объявления)
**Domain:** Веб-маркетплейс частных объявлений (private-only classifieds, RU-язычный, web-first, до 1 000 000 пользователей)
**Researched:** 2026-11-18
**Confidence:** MEDIUM (факты стека — HIGH; фичи/архитектура/подводные камни — MEDIUM с перекрёстным подтверждением; см. Confidence Assessment)

## Executive Summary

Продукт — классифайдс-платформа «только для частных лиц», читаемый на порядки чаще, чем пишемый домен с жёсткими лимитами PRD (≤10 активных объявлений, тексты 128/512 символов, снятие с публикации = удаление строки из БД). Все четыре исследования сходятся в одном: эксперты строят такие продукты как **модульный монолит с одной реляционной БД (PostgreSQL)**, поиск стартует на встроенном FTS с русской конфигурацией, мессенджер — HTTP-first с апгрейдом до realtime позже. Микросервисы, Elasticsearch и WebSocket-инфраструктура с первого дня — документированные анти-паттерны для greenfield-маркетплейса такого масштаба (≤10 млн строк, десятки–сотни RPS).

Рекомендуемый стек — **Вариант A: TypeScript-монолит NestJS 12 + Next.js 16 (SSR/SEO) + PostgreSQL 18 + Prisma 7 + Redis 8**; жизнеспособные альтернативы — Django 5.2 LTS (если решающим будет бесплатный admin) и Kotlin/Spring Boot 4.1. **Но правило репозитория (AGENTS.md) делает выбор стека явным ранним решением пользователя, а не фактом roadmap'а** — фаза 1 обязана зафиксировать A/B/C через ADR до какого-либо scaffold. Порядок работ диктуют зависимости данных и «правило инвариантов»: справочники (рубрикатор, города) до пользовательских фич; auth как фундамент (в PRD отсутствует); квота ≤10 — атомарный счётчик в БД; политика hard delete + снапшот для сообщений закладывается в схему до мессенджера, потому что retrofit стоит миграцию накопленных данных.

Ключевые риски и митигации: (1) **гонка лимита ≤10** — арбитраж только на стороне БД в одной транзакции + барьерный конкурентный тест как критерий приёмки; (2) **hard delete ломает переписку** — снапшот-поля заголовка/цены + `ON DELETE SET NULL` с первой версии схемы messages; (3) **поиск, деградирующий на объёме** — FTS с конфигурацией `russian`, keyset-пагинация и составные индексы с самого начала, приёмка по нагрузочному тесту на 100k+ строк; (4) **два пробела PRD** — админ-модерация и анти-абьюз мессенджера: оба дёшевы до запуска и дороги после (репутационно); (5) **утечка телефонов** — PII только аутентифицированным и по действию, проверяется анонимным curl-тестом.

## Key Findings

### Recommended Stack

Правило репозитория: язык/фреймворк не выбираются без явного согласия пользователя — STACK.md даёт одну основную рекомендацию и две альтернативы из других экосистем, финальный выбор за пользователем на фазе 1. Версии проверены по живым реестрам (npm, endoflife.date, postgresql.org, GitHub Releases) — это HIGH-факты. Обоснование всех трёх вариантов общее: данные строго реляционные, масштаб мал (1 млн пользователей ≠ 1 млн активных; квота ≤10 математически ограничивает размер главной таблицы), SEO — главный канал трафика (нужен SSR).

**Core technologies (Вариант A, основная рекомендация):**
- PostgreSQL 18 — единственная основная БД: дерево рубрикатора (self-FK), справочник городов, FK объявлений; лимиты PRD ложатся в типы; partial unique index + констрейнт для квоты ≤10; встроенный FTS (конфигурация `russian`, GIN, `websearch_to_tsquery`) закрывает поиск на старте без новой инфраструктуры
- NestJS 12 — модульный монолит: DI, guards/pipes, конвенции особенно ценны при генерации кода агентами; Node 26 LTS (допустимо 24 LTS — уже стоит на хосте)
- Next.js 16 + React 19 — SSR/ISR для страниц объявлений и категорий (SEO обязателен), App Router/RSC; SPA-без-SSR убивает индексацию
- Prisma 7 (+ pg для raw FTS/индексов) — типобезопасные запросы и декларативные миграции; альтернатива Drizzle — но не смешивать
- Redis 8.10 (или Valkey 8 при BSD-политике) — сессии, кэш справочников, rate-limit; AGPL-опция для внутреннего сервера не триггерится
- Zod 4 — единая валидация лимитов 128/512/≤10 на API и в формах (не смешивать с class-validator)
- Vitest 5 + Playwright 1.65 — юнит/интеграционные + E2E (сценарий «создать→опубликовать→снять→строка удалена»)

**Альтернативы:** Вариант B — Python/Django 5.2 LTS + DRF (если главный приоритет — Django Admin из коробки: рубрикатор и города — это две админ-CRUD-сущности PRD); Вариант C — Kotlin + Spring Boot 4.1 / JDK 25–27 (преимущество JVM для этого домена не реализуется, итерации медленнее). **Критичные версии:** PostgreSQL 18 (PG 19 — только RC), Node ≥ 20, RSC требуют React 19; Meilisearch 1.57 — только когда PG FTS перестанет хватать.

### Expected Features

Ядро категоризации: «только частные лица, без коммерциализации» — ряд стандартных функций индустрии (платное продвижение, бизнес-аккаунты, отзывы) являются **анти-фичами по определению**, а не упущениями. Отдельная ценность исследования — карта пробелов PRD: несколько table-stakes функций в нём отсутствуют и требуют решения на requirements.

**Must have (table stakes):**
- Регистрация/аутентификация + подтверждение e-mail — **не описано в PRD** (только роли); фундамент всех пользовательских фич
- Listing CRUD (заголовок ≤128, описание ≤512, цена, город, категория) + публикация/снятие с лимитом ≤10 и hard delete — из PRD
- Поиск + фильтры (категория/город/цена) + сортировка (дата/цена) + пагинация — PRD заявляет только «поиск», без деталей; без фильтров и пагинации поиск не живёт
- Страница объявления + страница продавца — точка входа в мессенджер
- Messaging по объявлению (≤512) + **email-уведомления о новых сообщениях** — уведомления не в PRD, критический пробел: без них мессенджинг мёртв
- Фотография объявления (минимум 1) — **не в PRD, крупнейший продуктовый пробел** против всех конкурентов; настоятельно рекомендовано добавить на requirements
- Admin: дерево категорий + справочник городов — из PRD
- Responsive web (75%+ мобильного трафика) и SEO-дружественные URL — дёшево сразу, дорого переделывать

**Should have (competitive):**
- Лимит ≤10 активных — превентивный анти-спам (главная боль Avito: дилеры заливают выдачу фейками)
- Равная видимость без платных бустов — продаётся как фича: «у нас нельзя купить видимость»
- Маскировка контактов в чате — v1.x, триггер: первые случаи парсинга/спама
- Прозрачная сортировка по дате — предсказуемость как обещание бренда

**Defer (v2+):** favorites, saved searches + алерты, счётчик просмотров, гео-радиус, мобильные приложения, SMS-верификация, realtime-транспорт сообщений (WebSocket).

**Anti-features (не строить никогда):** бизнес-аккаунты, платное продвижение/поднятия, платежи/эскроу/доставка, отзывы и рейтинги, аукционы, AI-модерация, автоподнятие/репосты.

### Architecture Approach

Консенсус источников: модульный монолит + одна реляционная БД, с заранее спроектированными швами для будущего выделения поиска (интерфейс `SearchIndex` + outbox) и realtime-транспорта сообщений. Модули владеют своими таблицами; межмодульный доступ — только через контракты. Инварианты (квота, hard delete, ссылочная целостность) проектируются в фазе-владельце таблицы — retrofit дороже в разы.

**Major components:**
1. Identity & Profile — регистрация, auth, профиль (имя/телефон/e-mail — обязательные поля PRD)
2. Catalog (дерево категорий) — adjacency list (`parent_id`) + recursive CTE + денормализованный `path` для фильтра поддерева в поиске
3. Geo (города) — плоский справочник, кэшируется целиком, FK-only в объявлениях
4. Listings — lifecycle draft→published; **квота ≤10 — DB-arbitrated** (атомарный условный счётчик в той же транзакции); unpublish = честный `DELETE` + декремент
5. Search (read-side) — Phase 1: Postgres FTS + btree-фильтры; Phase 2: Meilisearch/Typesense через уже существующий шов
6. Messaging — диалоги по объявлению, **снапшот заголовка/цены + `listing_id ON DELETE SET NULL`** (переживает hard delete)
7. Admin Console — справочники + RESTRICT на удаление используемых записей + audit log
8. Indexer/Outbox — позже, при выделении поискового движка

Ключевые паттерны: DB-arbitrated quota (счётчик + CHECK + row-level lock сериализует конкурентные публикации); adjacency list + recursive CTE для админ-редактируемого дерева (nested sets — анти-паттерн: перенос ветки переписывает таблицу); SSR-first клиентский слой.

### Critical Pitfalls

1. **Гонка при проверке лимита ≤10** — check-then-insert на READ COMMITTED пропускает 11-е объявление при параллельных публикациях. Митигация: атомарный условный счётчик в БД в одной транзакции с публикацией + барьерный конкурентный автотест (N потоков при 9 активных → ровно 10) как критерий приёмки фазы.
2. **Hard delete против переписки** — CASCADE уничтожает историю покупателя, RESTRICT блокирует снятие публикации, FK без политики оставляет «дыры». Митигация: снапшот-поля (`listing_title`, `listing_price`) + `ON DELETE SET NULL` в схеме messages с первой версии; семантика «удалить» vs «снять с публикации» — в ADR до фазы мессенджера.
3. **Поиск, деградирующий с ростом каталога** — `LIKE '%…%'` (полный скан), OFFSET-пагинация (дубли на глубоких страницах), `COUNT(*)` на каждый запрос, дефолтная `english`-конфигурация FTS («диваны» не найдёт «диван»). Митигация: FTS с явной конфигурацией `russian` + GIN, keyset-пагинация, составные индексы `(status, city_id, category_path, created_at)`, кэш тоталов («500+»), нагрузочный приёмочный тест на 100k+ сидированных строк.
4. **Мессенджер без анти-абьюза** — PRD модерацию не предусматривает вообще; спам-волны начинаются сразу после публичного запуска. Митигация: в первой версии — лимиты частоты (429), серверная блокировка доставки, «пожаловаться» в журнал, cooldown после регистрации; маскировку контактов можно отложить.
5. **Рубрикатор и справочник городов** — nested sets ломают админ-правки; сырой GeoNames полон дублей. Митигация: adjacency list + защита от циклов при переносе + RESTRICT на удаление используемых категорий; города — FK-only с autocomplete, seed с дедупликацией, merge-инструмент дублей.

Дополнительно критично: утёкшие в анонимный HTML телефоны (PII только аутентифицированным, curl-автотест) и отсутствие у админа инструментов модерации (hide/ban/audit log) — оба помечены как пробелы PRD.

## Implications for Roadmap

На основе исследований предложена структура из 10 фаз (fine-гранулярность; фаза 9 — условная, зависит от решения о фото). Ключевое правило порядка: **инварианты попадают в план той фазы, где появляется владеющая ими таблица** — retrofit квоты или политики удаления после появления messaging/search дороже в разы.

### Phase 1: Фундамент — выбор стека и скелет проекта
**Rationale:** Правило AGENTS.md: язык/фреймворк не выбираются без явного согласия пользователя. Всё остальное блокировано этим решением — STACK.md дал варианты A/B/C с проверенными версиями, но выбор остаётся user gate. Миграции/конвенции дешевле заложить сразу.
**Delivers:** ADR с решением A (NestJS+Next.js+PG) / B (Django) / C (Kotlin/Spring); репозиторий-скелет монолита (модульная раскладка из ARCHITECTURE.md); docker-compose (postgres 18 + redis); CI (lint + typecheck + test); механизм миграций; health-check.
**Addresses:** открывает все P1-фичи (инфраструктурная фаза).
**Avoids:** анти-паттерн «микросервисы + Kubernetes с первого дня»; случайный scaffold без конвенций.

### Phase 2: Identity & Profile (Auth)
**Rationale:** Auth — фундамент всех пользовательских фич (граф зависимостей FEATURES.md), при этом он отсутствует в PRD — пробел закрывается первым, а не «по ходу».
**Delivers:** регистрация/вход/сброс пароля + подтверждение e-mail; профиль (имя, телефон, e-mail); PII-политика: контакты видны только аутентифицированным и по явному действию.
**Addresses:** Auth + подтверждение email + Профиль (P1, не в PRD).
**Avoids:** pitfall «публичные контакты → спам-базы» (анонимный curl не содержит PII — автотест); enumeration при регистрации; бот-аккаунты (honeypot + лимиты).

### Phase 3: Admin-каталоги — рубрикатор + города
**Rationale:** Обязательные поля объявления ссылаются на оба справочника — пользовательские фичи не существуют без них. Admin-CRUD обоих технически идентичны (reference data + RESTRICT) — одна фаза.
**Delivers:** дерево категорий (adjacency list + recursive CTE + `path`-денормализация сразу — retrofit дорог); справочник городов с seed'ом и дедупликацией + autocomplete с alias'ами; RESTRICT на удаление используемых записей + счётчики использования; кэш с инвалидцией по правке; admin UI.
**Addresses:** Admin: дерево категорий + справочник городов (P1, из PRD).
**Avoids:** pitfall «nested sets в редактируемом дереве» (перенос ветки, циклы); pitfall «мусор в справочнике городов» (дубли/транслит); UX «кладбище пустых рубрик».

### Phase 4: Объявления — CRUD + публикация/снятие + квота ≤10
**Rationale:** Ядро домена. Правило инвариантов: квота, hard delete и ссылочная политика для будущих диалогов проектируются здесь — это самая дешёвая точка их закладки.
**Delivers:** Listing CRUD с серверной валидацией лимитов (128/512, Uniode-safe); state machine draft→published; публикация с атомарной квотой (`UPDATE ... WHERE active_count < 10` в одной транзакции); unpublish = `DELETE` + декремент; составные индексы под будущий поиск; ADR «удалить vs снять с публикации».
**Addresses:** Listing CRUD + Публикация с лимитом ≤10 (P1, из PRD).
**Avoids:** pitfall №1 «гонка лимита» (барьерный конкурентный тест в приёмке); pitfall №2 закладывается здесь — контракт снапшота и `ON DELETE SET NULL` для фазы мессенджера; техдолг «проверка лимита только в приложении» (never acceptable).

### Phase 5: Публичные страницы — объявление + продавец (SSR/SEO)
**Rationale:** Результат фазы 4 должен иметь точку входа; SSR — главный канал классифайдсов (органический поиск), закладывается до поисковой выдачи, чтобы она вела на живые страницы.
**Delivers:** страница объявления; страница продавца («другие объявления»); SEO-URL (`/city/category/slug`), sitemap; responsive; «показать телефон» только для авторизованных; warning перед безвозвратным снятием с публикации + черновик-копия.
**Addresses:** Страница объявления + продавца, responsive, SEO-дружественные URL (P1, не в PRD).
**Avoids:** pitfall «телефон в анонимном HTML» (curl-автотест); UX-шок безвозвратного удаления.

### Phase 6: Поиск — FTS + фильтры + сортировка + пагинация
**Rationale:** Требует наполненных listings и индексов из фазы 4; приносит первую покупательскую ценность «найти чужое объявление» (ядро PRD).
**Delivers:** PG FTS с явной конфигурацией `russian` + GIN по `to_tsvector(title || description)`; фильтры (поддерево категорий через `path`, город, диапазон цены); сортировка (дата/цена/релевантность — прозрачная, без платных бустов); keyset-пагинация; кэш/оценка тоталов; приёмка — нагрузочный тест на 100k+ сидированных строк с бюджетом p95.
**Addresses:** Search + фильтры + сортировка + пагинация (P1; в PRD только «поиск» без деталей).
**Avoids:** pitfall №5 «деградация поиска» (LIKE '%…%', OFFSET, COUNT(*), english-стеммер — все четыре механизма исключены конструкцией).

### Phase 7: Мессенджер + email-уведомления + базовый анти-абьюз
**Rationale:** Требует auth + страницу объявления (контекст «per-listing conversation»). Анти-абьюз-минимум обязан войти в первую версию мессенджера — включение после спам-волны технически дёшево, но репутационно катастрофично.
**Delivers:** диалоги по объявлению со снапшотом (`listing_title`, `listing_price`) + `listing_id ON DELETE SET NULL`; сообщения ≤512 с серверной валидацией; непрочитанные; email-уведомления со ссылкой на диалог (отправляющий домен + SPF/DKIM/DMARC, транзакционный провайдер, метрики bounce); лимиты частоты (429), серверная блокировка доставки, «пожаловаться» в журнал, cooldown после регистрации.
**Addresses:** Messaging + уведомления (P1 + критический пробел PRD); зачаток Report abuse (P2).
**Avoids:** pitfall №2 «ретрофит снапшота = миграция накопленных сообщений» (поля уже в схеме с фазы 4); pitfall №6 «мессенджер без анти-абьюза»; integration gotcha email-доставки; IDOR на `/messages/:id`.

### Phase 8: Админ-модерация + audit log (закрытие пробела PRD)
**Rationale:** Помеченный исследованием PRD-гэп: PRD даёт админу только каталоги, но операционно первые же инциденты (фейковые лоты, спам-аккаунты, жалобы) требуют hide/ban. Требует источников сигналов — report из фазы 7; обязательно до публичного запуска.
**Delivers:** скрытие/снятие чужого объявления админом; блокировка пользователя (запрет публикации и доставки сообщений на уровне сервера); журнал админ-действий (audit log); очередь жалоб.
**Addresses:** Admin: управление пользователями и контентом (P2 формально, операционно критично к запуску; не в PRD — требует одобрения пользователем); Report abuse полностью.
**Avoids:** pitfall №7 «единственный ответ на инцидент — прямой доступ к БД при безвозвратных удалениях»; security mistake «админка без audit log».

### Phase 9: Фотографии объявлений (УСЛОВНАЯ — решение на requirements)
**Rationale:** Крупнейший продуктовый пробел против всех конкурентов (FEATURES: текст-only объявление выглядит подозрительно, клик получает фото). В PRD отсутствует — вносится только по явному решению пользователя; при отказе фаза исключается без последствий для остальных.
**Delivers:** загрузка ≥1 фото к объявлению; S3-совместимое хранилище + CDN + сервис-ресайзер; каскадирование удаления блобов при unpublish.
**Addresses:** Фото объявлений (P1-рекомендация исследования, нет в PRD).
**Avoids:** анти-паттерн «блобы в PostgreSQL»; рассинхрон blobs/строк при hard delete.
**Uses:** внешний S3-совместимый сервис (MinIO self-hosted / облачный).

### Phase 10: Запускная готовность — security-проход и приёмочные тесты
**Rationale:** Чеклист «Looks Done But Isn't» из PITFALLS.md — финальная верификация инвариантов до публичного запуска; дешёвая фаза с высокой страховой ценностью.
**Delivers:** IDOR-тесты (пользователь B не читает/не правит сущности A); конкурентный тест квоты; анонимный curl страниц/API без PII; rate limit на все write-эндпоинты; honeypot, CAPTCHA точечно при признаках ботов; E2E Playwright («создать→опубликовать→снять→строка удалена из БД»); мониторинг доставляемости почты.
**Addresses:** верификация всех P1 перед запуском.
**Avoids:** security mistakes (IDOR, enumeration, отсутствие лимитов); «выглядит готовым, но не готово».

### Phase Ordering Rationale

- **Зависимости данных диктуют порядок:** auth → справочники → объявления → страницы/поиск → мессенджер (граф зависимостей FEATURES.md и Suggested Build Order ARCHITECTURE.md сходятся). Admin-каталоги строго до пользовательских фич: поля объявления ссылаются на оба справочника по FK.
- **Правило инвариантов:** квота/hard delete/`SET NULL`-политика появляются в фазе-владельце таблицы (фаза 4); мессенджер (фаза 7) строится поверх уже жёсткой политики — это единственный способ избежать миграций накопленных данных.
- **Auth раньше пользовательских фич,** хотя его нет в PRD: без него не существует ни одна фича (FEATURES Dependency Notes).
- **Анти-абьюз внутри фазы мессенджера,** а не отдельной фазой «потом»: лимиты и блокировка до публичного запуска — никогда не после (PITFALLS: «на публичном запуске — никогда»).
- **Админ-модерация после мессенджера** (нужны сигналы report), но до запуска; фото — условная фаза, изолированная от критического пути.
- **Сквозные SEO/SSR-решения** закладываются в фазах 5–6: URL-структуру и SSR дёшево сделать сразу и дорого переделывать потом.

### Gaps to Address

- **Выбор стека (A/B/C):** user gate фазы 1 — roadmap обязан держать это открытым решением, а не фактом; не выбирать scaffold до ADR.

- **Анти-абьюз мессенджера:** нет в PRD — минимальный набор (лимиты/блокировка/report) должен быть одобрен как обязательная часть фазы 7.

- **Семантика «удалить» vs «снять с публикации»:** двусмысленность PRD — зафиксировать в ADR до фазы 4/7 (обе операции удаляют строку? что происходит с черновиками?).
- **Детали поиска:** фильтры/сортировка/пагинация в PRD не заявлены — подтвердить состав на requirements (фаза 6).
- **Email-провайдер и домен отправки:** рынок не исследовался (только паттерны доставляемости) — research на фазе 7.
