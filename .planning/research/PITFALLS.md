# Pitfalls Research

**Domain:** Private classifieds web marketplace (объявления только от частных лиц)
**Researched:** 2026-11-18
**Confidence:** MEDIUM (ключевые технические утверждения перекрёстно проверены по 2+ независимым источникам; оценки метрик из vendor-блогов — LOW, помечены отдельно)

## Critical Pitfalls

### Pitfall 1: Гонка при проверке лимита «не более 10 опубликованных объявлений»

**What goes wrong:**
Публикация реализуется как «прочитать COUNT активных объявлений пользователя → если < 10, вставить». Два параллельных запроса публикации (двойной клик, две вкладки, два устройства, retry клиента) при 9 активных оба видят «9 < 10» и оба вставляют — становится 11. Лимит из PRD нарушается молча, воспроизводится спорадически и не ловится юнит-тестами с последовательными запросами.

**Why it happens:**
На уровне изоляции по умолчанию (READ COMMITTED в PostgreSQL/MySQL) каждый запрос видит снимок данных на момент старта; между SELECT и INSERT нет никакого барьера. Разработчики проверяют лимит в приложении, потому что «ограничение количества строк» нельзя выразить простым UNIQUE-констрейнтом (UNIQUE работает для лимита 1 через partial index `WHERE is_active`, но не для лимита 10).

**How to avoid:**
Один из способов, обязательно на стороне БД и в той же транзакции, что и публикация:
- атомарный условный счётчик: отдельная колонка/таблица `users.active_listings_count`, публикация выполняется как `UPDATE users SET active_listings_count = active_listings_count + 1 WHERE id = :uid AND active_listings_count < 10` — если затронуто 0 строк, отказ с понятной ошибкой; снятие с публикации уменьшает счётчик;
- либо `SELECT ... FOR UPDATE` по строке пользователя перед проверкой;
- либо SERIALIZABLE-изоляция с обработкой retry.
Завести автотест: барьерный конкурентный запуск N публикаций при 9 активных (N потоков стартуют одновременно), assert — ровно 10.

**Warning signs:**
В коде публикации паттерн `count = repo.countActive(uid); if (count >= 10) throw; repo.publish(...)` без блокировок; в ревью схемы нет ни счётчика, ни FOR UPDATE; в тестах нет конкурентных сценариев.

**Phase to address:**
Фаза «Объявления: публикация/снятие с публикации» — механизм должен попасть в сам план фазы и в её UAT (конкурентный тест как критерий приёмки).

### Pitfall 2: Снятие с публикации = hard delete против ссылочной целостности сообщений

**What goes wrong:**
PRD прямо требует: снятое с публикации объявление **удаляется из БД** (архива нет). При этом сообщения привязаны к объявлениям («пишет сообщения продавцам»). Если сообщения хранят `listing_id` с FK:
- `ON DELETE CASCADE` — снятие продавцом публикации уничтожает переписку покупателя (входящие обнуляются, история спора исчезает);
- `ON DELETE RESTRICT` — владелец вообще не может снять объявление, пока есть хоть одно сообщение (нарушение требования PRD);
- без FK — осиротевшие `listing_id`, UI рендерит «дыры» или падает.

Отдельная неоднозначность PRD: «пользователь удаляет свои объявления» и «снимает с публикации (удаление из БД)» — две разные операции с неопределённой семантикой удаления.

**Why it happens:**
Требование «удаление из БД» трактуется как запрет на soft-delete объявлений вообще, и это экстраполируют на всю модель данных. Но требование касается строки таблицы объявлений, а не контекста переписки.

**How to avoid:**
Снапшот-денормализация в момент отправки сообщения: в сообщении/треде хранить копию ключевых полей (`listing_title`, `listing_price`, `city_name`, `category_name` на момент отправки), а `listing_id` — `ON DELETE SET NULL`. Тогда строка объявления честно удаляется из БД, а переписка остаётся осмысленной («Объявление снято с публикации: iPhone 13, 45 000 ₽»). Правило: сообщения никогда не зависят от живой строки объявления критически. Тот же снапшот нужен для отображения «продано/снято» в треде. Зафиксировать в решении (ADR) семантику «удалить» vs «снять с публикации» до фазы сообщений.

**Warning signs:**
В схеме `messages.listing_id` без снапшот-полей; обсуждения «что показывать в чате после удаления объявления» возникают после реализации мессенджера; тест-кейсы не покрывают «снятие с публикации при существующей переписке».

**Phase to address:**
Самая ранняя фаза проектирования модели данных (до фазы мессенджера): снапшот-поля закладываются в схему messages сразу — ретрофит позже означает миграцию уже накопленных сообщений.

### Pitfall 3: Неправильная модель иерархического рубрикатора (категории)

**What goes wrong:**
Для дерева категорий выбирают nested sets / MPTT («чтобы поддерево выбиралось одним запросом»), а рубрикатор — **редактируемая админом** сущность: перенос ветки при nested sets переписывает левые/правые значения большой части таблицы и блокирует её на время; классические баги — цикл (категорию перемещают под её собственного потомка, дерево зацикливается), удаление категории, на которую ссылаются активные объявления (осиротевшие `category_id` или каскад, сносящий объявления), «светящиеся» пустые узлы.

**Why it happens:**
Статьи про иерархии хвалят nested sets за скорость чтения поддеревьев, не подчёркивая цену записи; в greenfield-проекте нет статистики реальных запросов, и оптимизируют не ту операцию (у админского рубрикатора записи редки, но критичны по корректности, а чтение дерева и так дёшево при сотнях узлов).

**How to avoid:**
Adjacency list (`parent_id`) + рекурсивные CTE — стандарт для админ-редактируемых каталогов; дерево маленькое (сотни–тысячи узлов), его можно кэшировать целиком и инвалидировать по событию изменения. Защита от циклов: при перемещении проверять, что новый родитель не потомок перемещаемого узла (один рекурсивный запрос). Удаление категории: `RESTRICT`, если есть объявления/дети; явный flow «перенести объявления в другую категорию, затем удалить». Материализацию пути/подсчёт потомков добавить позже, только если поддеревья станут горячими.

**Warning signs:**
В схеме категорий колонки `lft/rgt` (или `path` без плана синхронизации при переносе); в админ-UI нет операции перемещения узла (значит, её и не протестируют); в плане нет теста «перенести подкатегорию в другой родитель».

**Phase to address:**
Фаза «Рубрикатор (админ)»: выбор модели — часть плана фазы; тесты move/rename/delete с активными объявлениями — критерий приёмки.

### Pitfall 4: Справочник городов — качество данных

**What goes wrong:**
Город в объявлении становится мусорным: дубли («Саратов» и «Саратов.» и «г. Саратов»), один город в разных регионах, переименования, альтернативные написания/транслитерация («СПб» vs «Санкт-Петербург», «Moskva»). Поиск и фильтрация по городу — основной сценарий классифайдса — ломаются: фильтр «Москва» не находит объявления «Москва г.». Открытые датасеты (GeoNames) документированно содержат дубли городов и смесь населённых пунктов с регионами и venue'ами, а таблица альтернативных названий нестандартна по составу.

**Why it happens:**
Город хранят как текстовое поле в объявлении (быстро для MVP) или импортируют сырой публичный дамп без дедупликации; справочник ведёт админ вручную без процедур слияния.

**How to avoid:**
Город в объявлении — только FK на справочник, выбор через autocomplete с сервера (не free text, не `<select>` на 150k городов). Справочник: уникальный индекс на (name, region), связь с регионом/субъектом, alias-таблица для поиска альтернативных написаний, стабильные ID не зависящие от переименований. Если импортируют GeoNames — фильтрация по feature class «населённый пункт», проход дедупликации, и всё равно финальный справочник куррируется админом. Процедура merge дублей (обновить FK у объявлений) — обязательна админ-инструментом.

**Warning signs:**
`listing.city` типа VARCHAR; в админке городов нет поиска/дедупликации; автокомплит ищет только по точному имени без alias'ов.

**Phase to address:**
Фаза «Справочник городов (админ)» + фаза создания объявления (там FK и autocomplete). Seed справочника с дедупликацией — часть фазы, а не «потом».

### Pitfall 5: Поиск, деградирующий с ростом каталога (LIKE '%…%', OFFSET, COUNT(*), не тот стеммер)

**What goes wrong:**
Поиск по заголовку/описанию делают `LIKE '%слово%'` — лидирующий wildcard не использует B-tree-индекс, запрос превращается в полный скан таблицы. К нему добавляют `OFFSET/LIMIT` (глубокие страницы сканируют и выбрасывают все предыдущие строки; вставки во время листания дублируют/пропускают записи) и `COUNT(*)` на каждый запрос ради «страниц N из M». Отдельно для русского текста: PostgreSQL FTS по умолчанию использует конфигурацию `english` — поиск «диваны» не найдёт «диван», стемминг и стоп-слова будут английскими.

**Why it happens:**
На демо-данных (сотни строк) LIKE мгновенный; деградация линейна по объёму и проявляется на проде при десятках–сотнях тысяч объявлений, когда p95 поиска уже съедает бюджет. NFR «до 1 млн пользователей» в проекте заявлен явно — масштаб, на котором это гарантированно стреляет.

**How to avoid:**
- Полнотекстовый поиск из первой версии фазы поиска: встроенный FTS БД с явной конфигурацией `russian` (snowball-стеммер есть в pg_catalog) или trigram-индекс (pg_trgm) для частичных совпадений; внешний движок (Elasticsearch/Meili) — только когда встроенного перестанет хватать (он добавляет sync-пайплайн и ops-бремя).
- Пагинация keyset/cursor: `WHERE (created_at, id) < (:last_seen)` по составному индексу; OFFSET ограничить первыми страницами, «страницу 1000» не показывать.
- Составные индексы под фильтры поиска с самого начала: `(status, city_id, category_id, created_at)` и т.п.
- COUNT тоталов: кэшировать/оценивать/ограничивать («больше 500 результатов»).
- Нагрузочный приёмочный тест фазы: сидировать 100k+ объявлений и мерить p95.

**Warning signs:**
В коде поиска `LIKE '%' || :q || '%'`; в API списков `page`/`size` без курсора; фронт показывает точное число страниц; FTS-конфигурация не указана явно.

**Phase to address:**
Индексы и структура — уже в фазе «Объявления» (модель данных); сама реализация — фаза «Поиск». Приёмка поиска — по нагрузочному тесту на сидированных данных.

### Pitfall 6: Мессенджер без анти-абьюза: спам, сбор контактов, увод сделок

**What goes wrong:**
User-to-user сообщения выпускают «чистыми»: без лимитов частоты, без блокировки, без жалобы. Реальные паттерны abuse (по опыту маркетплейсов): копипаст-спам-рассылки по продавцам, фишинговые ссылки, сбор телефонов/email для увода сделки и оплаты вне площадки, харассмент после блокировки (если блокировка только прячет тред в UI, но не останавливает доставку — она не работает). PRD модерацию не предусматривает вообще — значит, контроля ноль с самого старта.

**Why it happens:**
Модерация не в scope, поэтому и базовые технические пределы не закладывают; «лимиты — это UX-фрикция». Между тем rate limit — самый дешёвый и технический контроль, не требующий модерационной команды; волны спама начинаются сразу после публичного запуска (кейсы Sharetribe: спамеры рассылали сообщения автоматизацией через бэкенд площадки; Facebook Marketplace ограничивает mass-outreach).

**How to avoid:**
Минимальный набор в первую версию мессенджера (без модерации людьми): (1) лимит новых тредов/дней на аккаунт (порядка единиц–десятков) и лимит сообщений/минуту; (2) cooldown между регистрацией и первым сообщением; (3) блокировка, которая реально останавливает доставку на уровне API; (4) одна кнопка «пожаловаться» с записью в журнал; (5) политика ссылок/вложений (что разрешено в 512-символьном сообщении); (6) решение о retention сообщений. Маскировку телефонов в сообщениях и классификаторы можно отложить — но лимиты и блокировка должны быть в первой версии.

**Warning signs:**
Эндпоинт отправки сообщения без per-user лимита; в плане фазы сообщений нет ни block, ни report; спам-фильтрация «потом, когда появится спам».

**Phase to address:**
Фаза «Сообщения» — контрлы входят в приёмку фазы (тест: превышение лимита → 429; блокировка → доставка запрещена на уровне сервера).

### Pitfall 7: У админа нет инструментов модерации объявлений и пользователей

**What goes wrong:**
PRD даёт админу только рубрикатор и справочник городов. Операционно первые же проблемы классифайдса — мошеннические объявления (overpayment-схемы, «слишком красивые» цены, фейковые лоты), спам-аккаунты, жалобы пользователей — требуют от админа возможности скрыть/удалить чужое объявление и заблокировать пользователя. Если этого нет, единственный ответ на инцидент — прямой доступ к БД (а по PRD объявления ещё и удаляются из БД безвозвратно — инцидент нельзя расследовать).

**Why it happens:**
Требования писались под контент-модель, а не под эксплуатацию; модерация осознанно вынесена из scope, но вместе с ней неявно выпали и базовые админ-операции.

**How to avoid:**
Включить в скоуп минимума: скрытие/снятие с публикации любого объявления админом, блокировка пользователя (запрет публикации и сообщений), журнал админ-действий (audit log). Это не модерационная команда и не классификаторы — это CRUD, дешёвый на фоне переделки позже. Явно зафиксировать в roadmap как gap относительно PRD (вопрос пользователю).

**Warning signs:**
В roadmap ни одна фаза не даёт админу власти над объявлениями/юзерами; приёмочные сценарии не включают «админ реагирует на жалобу».

**Phase to address:**
Фаза «Админ» (или дополнение к фазам объявлений/сообщений); как минимум — явное решение на этапе roadmap, задокументированное в PROJECT.md.

### Pitfall 8: Публичные контакты профиля → сбор баз, спам и дисинтермедиация

**What goes wrong:**
Профиль по PRD обязан содержать телефон и email. Если телефон рендерится на странице объявления для анонимов/краулеров, сайт становится готовой базой для спам-обзвонов и фишинга (телефон — токен для перехвата аккаунтов через сбросы и verification-коды; документированные схемы против продавцов классифайдсов), а сделка уводится в мессенджеры вне площадки. Плюс контент площадки скрейпят клоны-конкуренты.

**Why it happens:**
Телефон «для связи» воспринимают как фичу листинга, а не как PII; в B2C-классифайдсах телефон традиционно показывают, и это копируют без ограничений.

**How to avoid:**
Контакты видны только аутентифицированным пользователям, по явному действию («показать телефон»), с rate-limit на просмотры профилей; для анонимов/ботов телефон не попадает в HTML/API вообще. Проверять приёмкой: `curl` анонимной страницы объявления не содержит телефона. Формы — honeypot + лимиты на регистрацию против бот-баз.

**Warning signs:**
Телефон в шаблоне страницы объявления вне блока авторизации; API отдаёт profile.phone без проверки контекста.

**Phase to address:**
Фаза «Профиль пользователя» и фаза рендеринга страницы объявления; проверка — автоматическим тестом на анонимный запрос.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Поиск через `LIKE '%q%'` без FTS | Работает за час, ноль зависимостей | Полный скан при 100k+ строк; миграция на FTS требует backfill-индексов | Только если фаза поиска сразу закладывает FTS-план migration и лимит объёма до перехода |
| Сообщения без снапшота объявления | Меньше полей в схеме | Ретрофит = миграция накопленных сообщений, заголовки восстановимы только из бэкапов | Никогда — поле дешёвое на этапе схемы |
| Город строкой в объявлении | Быстрый старт без справочника | Фильтр/статистика по городу мусорные; конверсия в FK + чистка данных | Никогда — FK с первой версии дешевле, чем чистка позже |
| Пагинация OFFSET без cap | Просто, «страница N из M» в UI | Деградация глубоких страниц, дубли при вставках | Первые страницы (cap ~100–500 позиций) с keyset для остального |
| Проверка лимита 10 только в приложении | Нет schema-изменений | Гонки, «плавающие» 11-е объявление, потеря доверия к лимиту | Никогда для публикации; в MVP допустимо только при наличии атомарного счётчика в той же транзакции |
| Мессенджер без rate limit/block | Быстрее выпустить фичу | Спам-волна после запуска; репутационный ущерб выше стоимости лимитов | Только до публичного запуска; на публичном запуске — никогда |
| Регистрация без верификации email | Меньше шагов онбординга | Бот-аккаунты, спам-рассылки, невозможность восстановления доступа | Пресейл/закрытая бета; перед публичным запуском — включить |
| Кэш дерева категорий без инвалидации | Быстрый рендер рубрикатора | Админ правит рубрику — пользователи часами видят старое | Никогда — инвалидация по событию изменения (дерево меняется редко) |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| Email-отправка (верификация, уведомления) | Писать с «голого» домена без SPF/DKIM; не мониторить bounces | Отдельный отправляющий домен + DKIM/SPF/DMARC с старта; транзакционный провайдер; метрики доставки/bounce как алерты |
| Импорт GeoNames / открытых гео-датасетов | Залить сырой дамп в справочник | Фильтр только населённых пунктов, проход дедупликации, регионы отдельным уровнем, финальное куррирование админом; alias'ы отдельной таблицей |
| Внешний поисковый движок (ES/Meili и т.п.) | Подключить «по умолчанию для масштаба» без русских анализаторов и без sync-пайплайна | Начать со встроенного FTS БД (russian-конфигурация); внешний движок — по факту упирания, с явными анализаторами и индексацией на запись |
| CAPTCHA на все формы | Фрикция для всех легитимных пользователей | Honeypot + поведенческие лимиты сначала; CAPTCHA точечно (регистрация/публикация) при признаках ботов |
| SMS/верификация телефона | Обязать всех с первого дня | Телефон обязателен в профиле по PRD, но верификацию сделать опциональной/постепенной — стоимость и фрод RU-маршрутов |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| `LIKE '%term%'` по заголовку/описанию | p95 поиска растёт линейно с числом строк; CPU БД на 100% при боте | FTS (russian-конфигурация) или pg_trgm; искать только по заголовку+описанию объявлений | ~50–100k строк на скромном железе; гарантированно в зоне NFR проекта |
| OFFSET-пагинация списков/поиска | Глубокие страницы медленные; дубли записей при листании | Keyset-пагинация по (created_at, id); OFFSET только с cap | Заметно от ~10k строк, болезненно от 100k+ |
| `COUNT(*)` на каждый поисковый запрос | Медленные фильтрованные подсчёты; БД греет scans | Кэш/оценка тоталов, cap «500+», не показывать точное число страниц | Сотни тысяч строк с фильтрами |
| Рекурсивный CTE дерева категорий на каждый запрос | Дорогие повторные обходы дерева | Кэш всего дерева с инвалидацией по правке админом (дерево маленькое и меняется редко) | Обычно не ломается; ловит на высоком RPS главной/каталога |
| N+1 на списке объявлений (автор, город, категория) | Список из 20 объявлений даёт 60+ запросов | JOIN/Fetch заранее; выборка фиксированного набора полей | Заметно на любой первой нагрузке |
| Нет составных индексов под фильтры (город+категория+статус) | «Найти в городе X» сканирует всё | Индексы спроектировать в фазе модели данных вместе с запросами поиска | Первые десятки тысяч объявлений |
| Отсутствие лимитов на API списков (без пагинации) | Один запрос тянет всю таблицу | LIMIT обязателен на уровне API с первой версии | Первый же краулер/бот |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| IDOR: `/messages/:id`, `/listings/:id/edit`, операции с чужими сущностями без проверки владельца | Чтение чужой переписки, правка/снятие чужих объявлений | Проверка владельца на каждом эндпоинте сервером; автотесты «пользователь B не может тронуть сущность A» |
| Телефон/email в HTML и API для анонимов и ботов | Спам-базы, фишинг, перехват верификационных кодов, скрейпинг клонами | Контакты только аутентифицированным и по действию; анонимный `curl` не содержит PII (автотест) |
| Нет rate limit на регистрацию/публикацию/сообщения | Бот-волны фейковых объявлений и спама через легитимные эндпоинты | Лимиты на запись с первой публичной версии; honeypot на формах; cooldown новорега на сообщения |
| Перечисление (enumeration) email/телефонов при регистрации | Сбор валидных контактов перебором | Единообразные ответы («если аккаунт существует, мы отправили письмо»), общий тайминг |
| Админ-панель без audit log | Некому доказать кто что сделал; insider-инциденты нерасследуемы | Журнал админ-действий с первой версии админки |
| Телефон как единственный фактор входа/восстановления | SIM-swap / перехват кодов = захват аккаунта | Телефон — контакт, не единственный фактор; восстановление через email + код |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|------------------|
| Пустые категории и города на старте («кладбище рубрикатора») | Пользователь видит мёртвый каталог и уходит | Скрывать/деприоритизировать пустые узлы; сеять контент до запуска; счётчики только ненулевые |
| Онбординг из многих последовательных шагов до первого объявления (регистрация → верификация → профиль → фото → объявление) | Отсев на каждом шаге (задокументированные уроки классифайдсов: воронка разваливается) | Создать объявление как можно раньше (draft-режим), профиль дозаполнить по ходу |
| «Снять с публикации» = безвозвратное удаление без предупреждения | Пользователь в шоке: объявление и текст исчезли навсегда, надо вводить заново | Явный warning перед действием; отдельно сохранить черновик-копию (draft ≠ published, на лимит 10 не влияет), «опубликовать снова» |
| Неясная ошибка при попытке опубликовать 11-е | Пользователь не понимает, что делать | Сообщение с числом активных (10/10) и ссылками на них: какое снять, чтобы опубликовать новое |
| Тред сообщений после удаления объявления без контекста | «О чём речь?» в переписке | Снапшот заголовка/цены + бейдж «объявление снято с публикации» |
| Поиск без умолчаний (вся страна, все категории) | Ноль релевантности, «ничего не найти» | Умолчания: город пользователя + категория текущего раздела; пустая выдача с подсказками |

## "Looks Done But Isn't" Checklist

- [ ] **Публикация:** конкурентный тест — 2+ одновременных publish при 9 активных дают ровно 10, не 11
- [ ] **Снятие с публикации:** существующая переписка не ломается — снапшот заголовка/цены виден, ссылки ведут на «снято», счётчик активных уменьшился
- [ ] **Удаление vs снятие:** семантика двух операций зафиксирована и покрыта тестами (обе ли удаляют из БД, что происходит с черновиками)
- [ ] **Рубрикатор:** перенос категории под своего потомка отклонён; удаление категории с активными объявлениями запрещено/переносит; правка админом видна пользователям сразу (кэш инвалидируется)
- [ ] **Города:** дубль в справочнике находит и объединяет merge; autocomplete находит «СПб»/транслит; объявление невозможно сохранить с несуществующим city_id
- [ ] **Поиск:** 100k+ сидированных строк, p95 в бюджете; русский стемминг («диваны» → «диван»); листание без дублей при вставках
- [ ] **Сообщения:** лимит частоты возвращает 429; блокировка останавливает доставку на уровне сервера (не только скрывает UI); «пожаловаться» пишет в журнал
- [ ] **Контакты:** анонимный curl страницы объявления и API не содержит телефона/email
- [ ] **Лимиты полей:** 128/512/512 символов валидируются сервером (не только формой), включая Unicode
- [ ] **Доступ:** пользователь B не читает/не правит сущности пользователя A (IDAR-тесты на сообщениях и объявлениях)
- [ ] **Админ:** может скрыть чужое объявление и заблокировать пользователя; действие пишется в audit log

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Гонка лимита 10 (check-then-insert) | LOW | Ввести атомарный счётчик/FOR UPDATE; данные почти не повреждены — снять лишние 11-е через админ-запрос |
| Сообщения против hard-deleted объявлений | HIGH | Ретрофит снапшота = миграция накопленных сообщений; заголовки восстановимы только из бэкапов/логов; часть контекста утрачена безвозвратно |
| LIKE-поиск на объёме | MEDIUM | Миграция на FTS: добавить tsvector-колонку, backfill-переиндексацию (без даунтайма), переключить запросы |
| Nested sets в рубрикаторе | MEDIUM–HIGH | Конверсия модели (adjacency list), переписывание запросов поддеревьев, миграция данных |
| Дубли/мусор в справочнике городов | MEDIUM | Merge-инструмент: объединение записей с обновлением FK у объявлений, alias'ы для старых написаний |
| Спам-волна в мессенджере | LOW (технически) / HIGH (репутационно) | Включить лимиты постфактум, забанить волну, добавить report; вернуть доверие пользователей маркетингом |
| Отсутствие админ-модерации | LOW (инструменты) / HIGH (репутация) | Добавить hide/ban + audit log срочно; для расследования инцидентов поднимать бэкапы |
| Утёкшие телефоны (индексированы ботами) | HIGH | Убрать из анонимного рендера немедленно; ротация невозможна (номера реальные) — остаётся только минимизация последствий |

## Pitfall-to-Phase Mapping

| Pitfall | Prevention Phase | Verification |
|---------|------------------|--------------|
| Гонка ≤10 активных объявлений | Фаза «Объявления: публикация» | Конкурентный автотест (барьерный запуск N публикаций) как критерий приёмки |
| Hard delete vs сообщения | Фаза «Модель данных» (до мессенджера) | Ревью схемы messages: снапшот-поля + `ON DELETE SET NULL`; тест «unpublish при живой переписке» |
| Модель дерева рубрикатора | Фаза «Рубрикатор (админ)» | Схема на adjacency list; тесты move/rename/delete с активными объявлениями и циклами |
| Качество справочника городов | Фаза «Справочник городов» + фаза создания объявления | Seed с дедупликацией; тест autocomplete по алиасам; FK-only в объявлении |
| Деградация поиска | Фаза «Поиск» (+ индексы в фазе «Объявления») | Нагрузочный тест на 100k+ сидированных строк; русский стемминг; keyset-пагинация |
| Спам/абьюз мессенджера | Фаза «Сообщения» | Тесты 429 на лимитах; блокировка останавливает доставку серверно; report пишет журнал |
| Нет админ-модерации | Фаза «Админ» / решение на roadmap | Приёмочный сценарий: админ скрывает объявление и банит пользователя, действие в audit log |
| Публичные контакты | Фаза «Профиль» + рендер объявления | Автотест: анонимный запрос страницы/API не содержит PII |
