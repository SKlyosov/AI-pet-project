# Roadmap: Private Classifieds (Частные объявления)

## Overview

Путь от пустого greenfield-репозитория до публичного запуска классифайдс-платформы «только для частных лиц». Фаза 1 закрывает единственное блокирующее решение — явный выбор стека пользователем (ADR по вариантам A/B/C из research, правило AGENTS.md) — и закладывает скелет модульного монолита с CI и миграциями. Дальше порядок диктуют зависимости данных: аккаунты и профили (auth в PRD отсутствует — пробел закрывается первым) → справочники администратора, на которые ссылаются объявления → ядро домена с инвариантами (квота ≤10 атомарно в БД, снятие с публикации = hard delete, политика `ON DELETE SET NULL` + снапшот-поля для будущих диалогов — всё закладывается в фазе-владельце таблицы) → фотографии → публичные страницы (SSR/SEO) → поиск → мессенджер с анти-абьюзом → модерация с audit log → финальный security-проход и сквозная приёмка. Ретрофит инвариантов после появления messaging/search исключён конструкцией порядка.

### Phase 1: Фундамент — выбор стека и скелет проекта
**Goal**: Стек выбран явным решением пользователя и зафиксирован ADR; репозиторий-скелет модульного монолита собирается, проходит CI и поднимается одной командой
**Mode:** mvp
**Depends on**: Nothing (first phase)
**Requirements**: нет прямых v1-требований — инфраструктурная фаза, разблокирующая все остальные
**Success Criteria** (what must be TRUE):
  1. В репозитории лежит ADR с явным выбором стека из исследованных вариантов A (NestJS + Next.js + PostgreSQL) / B (Django) / C (Kotlin + Spring Boot) и обоснованием — выбор сделал пользователь, а не агент (правило AGENTS.md)
  2. Свежий клон репозитория поднимается одной командой: docker-compose запускает PostgreSQL и Redis, приложение отвечает на health-check
  3. CI на каждый пуш выполняет lint, typecheck и тесты; упавшая ступень делает пайплайн красным
  4. Механизм миграций БД работает: первая миграция воспроизводимо накатывается на чистую базу

### Phase 2: Аккаунты и профиль (Identity & Profile)
**Goal**: Пользователь получает аккаунт с подтверждённым e-mail и заполненным профилем; контакты продавца защищены PII-политикой с первого дня
**Mode:** mvp
**Depends on**: Phase 1
**Requirements**: AUTH-01, AUTH-02, AUTH-03, AUTH-04, AUTH-05, PROF-01, PROF-02
**Success Criteria** (what must be TRUE):
  1. Новый пользователь регистрируется с e-mail и паролем; неподтверждённый аккаунт не допускается к публикации, подтверждение — по ссылке из письма
  2. Пользователь входит и остаётся в системе между визитами; может выйти из системы
  3. Пользователь восстанавливает забытый пароль по ссылке из e-mail
  4. Пользователь заполняет профиль с обязательными полями: имя, телефон для связи, e-mail
  5. Телефон и e-mail продавца отдаются только аутентифицированным пользователям и только по явному действию («показать контакты»); анонимный запрос не содержит PII

### Phase 3: Справочники администратора (рубрикатор и города)
**Goal**: Администратор ведёт оба справочника, на которые ссылаются объявления; дерево категорий защищено от циклов, справочник городов — от дублей
**Mode:** mvp
**Depends on**: Phase 2
**Requirements**: ADMN-01, ADMN-02
**Success Criteria** (what must be TRUE):
  1. Администратор создаёт, переименовывает и перемещает категории; попытка сделать категорию потомком самой себя или своего потомка отклоняется (защита от циклов)
  2. Удаление категории, на которую ссылаются активные объявления, запрещено с понятным сообщением
  3. Администратор добавляет и переименовывает города, объединяет дубли; объявления при объединении сохраняют корректную ссылку на город
  4. Правки справочников сразу видны выбирающим их пользовательским формам — без пересборки или рестарта приложения (кэш с инвалидцией)

### Phase 4: Объявления — жизненный цикл и квота
**Goal**: Пользователь ведёт полный жизненный цикл объявления (черновик → публикация → редактирование → удаление/снятие) с атомарной квотой ≤10 и честным hard delete; схема БД закладывает инварианты для будущих фаз — снапшот-поля и `ON DELETE SET NULL` для диалогов, составные индексы под поиск
**Mode:** mvp
**Depends on**: Phase 3
**Requirements**: LIST-01, LIST-02, LIST-03, LIST-04, LIST-05, LIST-06
**Success Criteria** (what must be TRUE):
  1. Пользователь создаёт объявление с обязательными полями (город, категория, заголовок ≤128, описание ≤512, цена); превышение лимитов отклоняется сервером
  2. Объявление сохраняется как черновик: не опубликовано, не видно в публичном доступе и не считается в лимите 10
  3. Одновременно опубликовано не более 10 объявлений на пользователя: при параллельных публикациях на границе (9 активных + N конкурентных попыток) в БД остаётся ровно 10 — барьерный конкурентный тест зелёный
  4. Снятие объявления с публикации удаляет его из базы данных (hard delete: строки в БД больше нет)
  5. Пользователь редактирует и удаляет только собственные объявления; попытка доступа к чужим отклоняется

### Phase 5: Фотографии объявлений
**Goal**: Объявление публикуется с минимум одним фото; файлы хранятся вне БД и удаляются вместе с объявлением — без осиротевших блобов
**Mode:** mvp
**Depends on**: Phase 4
**Requirements**: PHOTO-01, PHOTO-02
**Success Criteria** (what must be TRUE):
  1. Пользователь загружает к объявлению минимум одно фото (может добавить или заменить); файл хранится вне БД (S3-совместимое хранилище) и доступен по стабильному URL
  2. Объявление без единого фото не может быть опубликовано
  3. После удаления или снятия объявления с публикации фото-файлы удаляются из хранилища (осиротевших блобов нет)
  4. Некорректные файлы (не изображение, превышение размера) отклоняются с понятной ошибкой; из оригинала автоматически готовятся производные размеры (ресайз)

### Phase 6: Публичные страницы (SSR/SEO)
**Goal**: Покупатель, включая анонимного, попадает на SEO-дружественную страницу объявления с фото и на страницу продавца; всё работает на мобильных; контакты раскрываются только аутентифицированным по явному действию
**Mode:** mvp
**Depends on**: Phase 5
**Requirements**: PAGE-01, PAGE-02, PAGE-03
**Success Criteria** (what must be TRUE):
  1. Анонимный посетитель открывает страницу объявления по SEO-дружественному URL (город/категория/заголовок); контент (заголовок, описание, цена, город, категория, фото) присутствует в серверном HTML без выполнения JS
  2. Покупатель открывает страницу продавца и видит его активные объявления
  3. Контакты продавца показываются на странице только аутентифицированному пользователю и только после явного действия («показать контакты»); в анонимно скачанном HTML PII отсутствует (curl-тест)
  4. Все страницы работоспособны на мобильных устройствах (responsive вёрстка)

### Phase 7: Поиск и выдача
**Goal**: Покупатель находит чужие объявления: полнотекстовый поиск с русской морфологией, комбинированные фильтры, сортировка и пагинация, не деградирующая на объёме
**Mode:** mvp
**Depends on**: Phase 6
**Requirements**: SRCH-01, SRCH-02, SRCH-03, SRCH-04
**Success Criteria** (what must be TRUE):
  1. Поисковый запрос находит объявления по заголовку и описанию с русской морфологией (запрос «диван» находит «диваны»)
  2. Выдача фильтруется по категории (включая поддерево), городу и диапазону цены; фильтры комбинируются
  3. Выдача сортируется по дате и по цене в обе стороны (возрастание/убывание)
  4. Пагинация не деградирует на глубоких страницах при 100k+ сидированных объявлениях (бюджет p95 зафиксирован приёмочным нагрузочным тестом); карточки выдачи показывают фото, заголовок, цену и город

### Phase 8: Мессенджер и уведомления
**Goal**: Покупатель и продавец переписываются по объявлению с e-mail-уведомлениями; диалог переживает удаление объявления; мессенджер защищён базовым анти-абьюзом с первой версии
**Mode:** mvp
**Depends on**: Phase 6
**Requirements**: MSG-01, MSG-02, MSG-03, MSG-04, MSG-05
**Success Criteria** (what must be TRUE):
  1. Аутентифицированный пользователь пишет продавцу сообщение по объявлению (≤512 символов, серверная валидация); диалог привязан к объявлению
  2. Пользователь видит список своих диалогов и непрочитанные сообщения
  3. Получатель нового сообщения получает e-mail со ссылкой на диалог
  4. После удаления объявления диалог сохраняется: видны снапшот заголовка и цены, стоит пометка «объявление удалено»
  5. Превышение частоты отправки отклоняется (429); заблокированным пользователям доставка сообщений запрещена на сервере

### Phase 9: Модерация и audit log
**Goal**: Администратор реагирует на инциденты без прямого доступа к БД: жалобы, скрытие чужих объявлений, блокировка пользователей — каждое действие в журнале
**Mode:** mvp
**Depends on**: Phase 8
**Requirements**: MODR-01, MODR-02, MODR-03, MODR-04
**Success Criteria** (what must be TRUE):
  1. Пользователь подаёт жалобу на объявление или сообщение; жалоба попадает в очередь модерации
  2. Администратор скрывает или снимает с публикации чужое объявление; оно исчезает из публичного доступа и поиска
  3. Администратор блокирует пользователя: заблокированный не может публиковать объявления, его сообщения не доставляются
  4. Каждое действие администратора фиксируется в журнале (кто, что, когда)

**UI hint**: yes

### Phase 10: Запускная готовность
**Goal**: Все инварианты v1 подтверждены сквозными приёмочными тестами до публичного запуска — «выглядит готовым» становится «проверено готовым»
**Mode:** mvp
**Depends on**: Phase 9
**Requirements**: нет новых — фаза верифицирует требования фаз 2–9 (сквозная приёмка перед запуском)
**Success Criteria** (what must be TRUE):
  1. IDOR-проверки зелёные: пользователь B не может читать или изменять сущности пользователя A (объявления, диалоги, профиль)
  2. Барьерный конкурентный тест квоты ≤10 проходит; E2E-сценарий «создать → опубликовать → снять → строки нет в БД» зелёный
  3. Анонимный обход всех публичных страниц и API не отдаёт PII; rate-limit стоит на всех write-эндпоинтах
  4. Доставляемость почты мониторится (bounce, жалобы); honeypot и точечная CAPTCHA срабатывают на признаках ботов
