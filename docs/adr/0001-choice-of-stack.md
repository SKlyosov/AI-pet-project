# ADR-0001: Choice of Technology Stack

## Status

Accepted — 2026-11-18

## Context

Проект — greenfield веб-сервис частных объявлений (RU-language, web-first, до 1 000 000 пользователей; требования и ограничения — `docs/PRD.md`). Исходного кода, манифестов и CI в репозитории нет; стек намеренно не выбирался до этой точки.

По правилу репозитория (AGENTS.md) язык/фреймворк не выбирается агентом самостоятельно: фаза research (`.planning/research/STACK.md`) подготовила одну основную рекомендацию и две жизнеспособные альтернативы с явными tradeoffs:

- **Вариант A** — TypeScript-монолит «NestJS + Next.js + PostgreSQL» (основная рекомендация research'а);
- **Вариант B** — Python / Django 5.2 LTS + Django REST Framework + PostgreSQL;
- **Вариант C** — JVM: Kotlin + Spring Boot + Spring Data JPA + PostgreSQL.

Выбор из вариантов A/B/C сделал **пользователь** (правило AGENTS.md и критерий приёмки SC-1 фазы 1 — решение пользователя, не агента).

## Decision

**Вариант B: Python / Django 5.2 LTS + Django REST Framework; PostgreSQL 18 — единственная RDBMS; Redis 8 — кэш/сессии/лимиты** (D-01). Решение принял пользователь явно из вариантов A/B/C; оно one-way — после появления миграций и кода смена стека означает переписывание проекта.

Состав решения (D-01…D-08 из контекста фазы 1):

- **D-01:** Стек — Вариант B: Python / Django 5.2 LTS + Django REST Framework; PostgreSQL 18 — единственная RDBMS; Redis 8 — кэш/сессии/лимиты.
- **D-02:** Django Admin принимается как админ-слой: обе админ-CRUD сущности PRD (рубрикатор, города) и будущая модерация (Phase 9) покрываются админкой; кастомная админка в v1 не строится — причина выбора варианта B.
- **D-03:** SSR через Django templates для SEO-страниц (фазы 5–6); JSON API через DRF — точечно (поиск, мессенджер, динамические формы). SPA-фронтенд не строим.
- **D-04:** Единая монорепа модульного монолита: один Django-проект с приложениями-модулями по границам домена (`accounts`, `catalog`, `geo`, `listings`, `search`, `messaging`, `moderation`) — граница модуля = владение своими таблицами.
- **D-05:** docker-compose: PostgreSQL 18 + Redis 8 + Django app (gunicorn) + health-check; объектное хранилище (MinIO/S3) не включается — добавляется в Phase 5 (фотографии).
- **D-06:** CI — GitHub Actions: ruff (lint) + mypy (typecheck, non-strict на старте) + pytest (tests) на каждый пуш/PR; упавшая ступень краснит пайплайн.
- **D-07:** Миграции — нативные Django migrations; первая миграция воспроизводимо накатывается на чистую базу.
- **D-08:** Python 3.13 (подтверждённая поддержка Django 5.2), WSGI/gunicorn — ASGI только при realtime (v2+).

## Alternatives Considered

- **Вариант A — NestJS 12 + Next.js 16 + PostgreSQL 18 (TypeScript, основная рекомендация research'а).** Отклонён пользователем: админ-слой (иерархический рубрикатор, справочник городов, будущая модерация) в экосистеме NestJS/Next.js пришлось бы строить руками — нет аналога Django Admin; два фреймворка (бэкенд + SSR-фронт) — больше движущихся частей и медленнее итерации для малой команды/агентного workflow.
- **Вариант C — Kotlin + Spring Boot 4.1 + Spring Data JPA + PostgreSQL 18 (JDK 25/27 LTS).** Отклонён пользователем: больше шаблонного кода и медленнее итерации для малой команды; для домена с жёсткими лимитами (заголовок ≤128, описание/сообщение ≤512, ≤10 опубликованных объявлений) и малыми данными преимущество JVM по пропускной способности не реализуется; фронт всё равно отдельный.
- **Причина выбора B:** Django Admin закрывает обе админ-CRUD сущности PRD (рубрикатор, города) без кастомной админки — «почти бесплатно» (01-CONTEXT.md § specific_ideas); плюс зрелые batteries (auth, forms, ORM+миграции) и LTS-линия.

## Consequences

Позитивные:

- **LTS до апреля 2028** — линия Django 5.2 получает security-поддержку до конца LTS-цикла; обновление до Django 6.x — отдельным осознанным решением после LTS-цикла.
- **Админка «почти бесплатно»** — рубрикатор и справочник городов (обе админ-CRUD сущности PRD) покрываются Django Admin без разработки кастомной админки; туда же ложится модерация Phase 9.
- **Батареи-в-комплекте** — auth, forms, ORM с миграциями, admin, CSRF-механизмы снижают объём собственной обвязки на старте.

Ограничения и осознанные риски (фиксируются, чтобы не переоткрывать):

- **Dev-БД фазы 1 — одноразовая (Pitfall 1 из research).** Фаза 1 прогоняет `migrate` со стандартным `auth.User`; кастомная User-модель (`AUTH_USER_MODEL`) вводится в Phase 2 **до появления пользовательских данных** и сопровождается пересозданием dev-тома командой `docker compose down -v`. Смена `AUTH_USER_MODEL` на непустой базе — рефактор-миграция повышенного риска; решение о сбросе dev-тома принято осознанно.
- **mypy пинится в линии 1.19** (`mypy==1.19.1`): django-stubs 5.2.9 объявляет протестированный диапазон `compatible-mypy: mypy>=1.13,<1.20` — mypy 2.x не использовать (резолвится без конфликта, но вне тестируемого диапазона django-stubs).
- **SSR на Django templates (D-03)** — переход на SPA-архитектуру в будущем затронет все шаблоны и клиентский слой (costly, отложено сознательно).
- **Монорепа модульного монолита (D-04)** — перегруппировка приложений затронет импорты и миграции (costly); границы модулей = границы таблиц, дисциплина импортов с первого дня.
